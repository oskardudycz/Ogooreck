### Q&A-1. Two decisions that the r1 resolution credits to answer 31 are not in `qa.md`, and the spec now goes against answer 30's `Host(...)` call

Quote: r1 Quality-3 resolution: "`Func` configure; host calls split by type". Q&A 31 lists only the rule that configuration happens before the first step. Q&A 30: "A base address, for example `Host(async () => app.GetEndpoint("api"))`". Q&A 27: "Every builder call is optional ...: `.Host`, ...". Spec: "It shares the configuration calls with `ApiSpecification` through a common base. Neither type exposes the other's host call." Spec: "A `Func` is used for `configure` ...". In the spec table, `Host(...)` is listed for `ApiSpecification<TProgram>` only. Java has a protected `catchUpTimeout` field, with no configure function and no host split.
Consequence: Oskar never chose the `Func` configure shape, the common base, or the removal of answer 30's `Host(Func<Task<Uri>>)` call. A user who follows answer 30's example gets a compile error. "Neither type exposes the other's host call" also suggests a non-generic host call that the table doesn't list.
Belongs to: qa
Resolution: fixed in r3: "Both (Recommended)" (answer 35).

### Q&A-2. Histograms: `ExpectMetric` sums the recorded values where Java counts them, and OTLP histograms are not read at all

Quote: Q&A 31 (the standing rule). Java `countOf`: `Timer timer -> timer.count()`, `DistributionSummary summary -> summary.count()`. Spec: "Delta measurements: the sum of the attributed values recorded after the baseline." Q&A 32 and spec: the decoder reads "sum and gauge data points" only.
Consequence: For an in-process `Histogram<double>` such as `http.server.request.duration`, `ExpectMetric(..., 1)` sums the durations (about 0.034) and fails. Over OTLP, the histogram is never decoded, so the check fails at the deadline. In-process and Aspire then differ, and both differ from Java.
Belongs to: qa
Resolution: fixed in r3: "Yes, as proposed" (answer 38). Histograms count measurements; OTLP histogram counts decoded.

### Q&A-3. `Eventually` drops the earlier attempts' trace ids from span and metric attribution, which no answer decides

Quote: Spec: "Spans belong to the test when their trace id is in the test's set: every Given step, and the When step's final attempt." Q&A 31: "Span attribution uses the trace ids of all the test's steps, Given and When".
Consequence: The r1 Q&A-1 failure comes back inside `Eventually`: a final-attempt span that was caused by a message from an earlier attempt has no handler span in the set, so `ExpectCorrelatedTrace` fails. Spans and measurements from earlier attempts also don't count for `ExpectTrace` and `ExpectMetric`.
Belongs to: qa
Resolution: fixed in r3: "Yes, as proposed" (answer 38).

### Quality-1. Shared configuration calls on the "common base" have no return type

Quote: "It shares the configuration calls with `ApiSpecification` through a common base."; "Configuration calls change the instance and return it."; "`Func<ApiSpecification<TProgram>, ApiSpecification<TProgram>> configure`"; AC 2.2.
Consequence: If the calls return the base type, `spec => spec.Deadline(x)` doesn't compile as that `Func`, and `For<Program>().Recording(...).Host(...)` doesn't compile at all. The developer must choose between:
- a base that is generic over its own type;
- each type re-declaring the calls;
- extension methods;
- a fixed order of calls.

The base is also unnamed, and the spec doesn't say whether `Given`/`When`/`Then` live on it.
Belongs to: spec
Resolution: fixed in r3: "Yes, as proposed" (answer 38).

### Quality-2. AC 27.5 and the Trace context rationale can't hold under the Java rules the spec adopts

Quote: "A When span caused by a message from a Given step can then be checked against the Given step's handler span."; AC 27.5; "`ExpectCorrelatedTrace()` ... uses the Java version's rules".
Consequence: Java's `SpanTree.isBelow` returns false when the trace ids differ. A span below the Given handler is then in the Given trace, not the When trace, so 27.5 can't be set up as written, and the rationale sentence is false. The other option is to allow causation across traces, which departs from Java and needs a rule the spec doesn't give.
Belongs to: qa
Resolution: fixed in r3: "Yes, as proposed" (answer 38). AC 27.5 now asserts the Java failure.

### Quality-3. AC 6.4 passes even if `.Json(...)` is ignored

Quote: 6.4 "... options serialize enums as numbers WHEN the response contains `"status":1` THEN `Body(new { status = OrderStatus.Placed })` matches".
Consequence: `JsonStringEnumConverter` accepts integers by default, so `"status":1` reads as `Placed` under any of the options. The test passes whether or not `Json(...)` works. The AC also doesn't say whether `Body` deserializes the response or serializes the expected value.
Belongs to: spec
Resolution: fixed in r3: "Yes, as proposed" (answer 38).

### Quality-4. In-process measurements with no `Activity.Current`: tag match or dropped?

Quote: "In-process measurements carry the trace id of `Activity.Current` ... count when that trace id is in the test's set. Measurements without a trace id, from observable instruments and OTLP data points, count by tag match only."
Consequence: A counter incremented in a background worker has `TraceId = null`. Should it be dropped, so `ExpectMetric` fails at the deadline, or counted by tag, so it counts other parallel tests' increments? The same rule decides how a custom source must fill `TraceId`.
Belongs to: qa
Resolution: fixed in r3: "Count by tags (Recommended)" (answer 36).

### Quality-5. An OTLP cumulative baseline can miss a Given step's increment, so the metric overshoots

Quote: "Before the When step, Ogooreck calls ... `Collect` and takes a metric baseline per series."; OTLP "`Collect` does nothing"; "A series with no baseline value counts from 0"; "fails at once if the increase exceeds it".
Consequence: When the Given step's export hasn't arrived at baseline time, the baseline is 0. The next export reports a cumulative 2, so `ExpectMetric(..., 1)` fails at once. That makes Aspire metric tests flaky, or the developer invents a wait the spec doesn't allow.
Belongs to: qa
Resolution: fixed in r3: "can we have 1 and opt in for 2?" (answer 37). Documented by default; opt-in `WaitForMetricsExport`.

### Quality-6. Telemetry source lifecycle: shared or per specification, and what `Start` means

Quote: "`TelemetrySources.InProcess`" (a property); "The specification starts the source"; "Disposal stops ... the telemetry source"; `void Start(Recorded<RecordedSpan>, Recorded<RecordedMeasurement>)`; "`OtlpReceiver.Start()` runs Kestrel"; 29.1 "`OtlpReceiver.Endpoint`".
Consequence:
- If `InProcess` is one shared instance, two fixtures start it with different recorders, and disposing one fixture stops the other's listeners.
- `Start` names two different things: starting Kestrel and attaching recorders.
- In AC 4.4, the receiver is created inside `configure`, but the address function needs its `Endpoint`, and the spec doesn't say how it reaches it.
Belongs to: spec
Resolution: fixed in r3: "Yes, as proposed" (answer 38).

### Quality-7. Non-string span attributes have no defined string form

Quote: decoder reads "string, int, double and bool attributes"; `RecordedSpan(..., IReadOnlyDictionary<string, string> Attributes)`.
Consequence: In-process, `true.ToString()` is `"True"`, and doubles format by culture. Java's `String.valueOf` gives `"true"`, and the OTLP decoder needs its own choice. The same `ExpectTrace` can then pass under Aspire and fail in-process.
Belongs to: spec
Resolution: fixed in r3: "Yes, as proposed" (answer 38).
