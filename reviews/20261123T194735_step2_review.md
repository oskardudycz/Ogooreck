### Step-1. The plain catch-up loop's "kept producing" check at the end of a round has no test

Quote: `CatchUpRunner.AfterStep`: `if (settings.RecordedCount == before) return; ct.ThrowIfCancellationRequested(); if (stopwatch.Elapsed >= settings.Deadline) throw KeptProducing(where, null);`. Spec, "Recording and catch-up": "Stop when a round adds no items. Past the deadline, fail with "The application kept producing messages for longer than {deadline}"". Plan 22.3: "a sample consumer republishes forever; failure after at least 2 s".
Consequence: 22.3 (`AppThatKeepsPublishing_FailsAtTheDeadlineSayingSo`) goes through `AppApi`'s wrapping catch-up, so it runs `AroundStep`, not this loop. `CatchUpFunctionThatNeverReturns_FailsAtTheDeadline` reaches the `!completed` branch; 22.2 ends after 4 quick rounds. No test runs the round-based deadline, the main deadline rule for a plain `Recording(recorded, read, catchUp)`. If that line broke, an app that keeps publishing would loop with no end and the suite would stay green. Fix: a test with a catch-up function that adds an item on every call and `Deadline(2 s)`.
Belongs to: implementation
Resolution: implementation: fix round.

### Step-2. Cancelling `Then` while a wrapping catch-up waits names the step as running, and no test covers it

Quote: `WhenApiSpecificationBuilder.Run`: `var running = "";` … `await catchUp.AroundStep(...)` … `running = "catch-up after the ";` … `$"Then was cancelled while the {running}{Where()} was running."`. `CatchUpRunner.AroundStep`: `if (ct.IsCancellationRequested) ExceptionDispatchInfo.Throw(failure ?? new OperationCanceledException(ct));`. Spec, "Failure messages": "the `OperationCanceledException` message says that `Then` was cancelled, and during which step or wait". qa 48: "while which step or wait".
Consequence: In the Wolverine setup the step often finishes and then `TrackActivity` waits for the cascade. Cancelling then gives "Then was cancelled while the When request POST … was running.", although the step had finished and the wait was the catch-up around it. This breaks qa 48. `CancellingThen_DuringCatchUp_NamesTheStepItFollows` covers only the plain `CatchUp` path; the cancellation branch in `AroundStep` never runs in a test.
Belongs to: implementation
Resolution: implementation: fix round.

### Step-3. With a wrapping catch-up, the deadline also bounds and cancels the step, and a wrapper that skips or repeats the step goes unnoticed

Quote: `CatchUpRunner.AroundStep`: `deadline.CancelAfter(settings.Deadline); … var running = Started(() => wrapped(deadline.Token));` and `throw StillRunning(where(), stepError)` ("The {where} was still running when the deadline of {deadline} passed…"). `AfterStep` then starts a second `CancelAfter(settings.Deadline)`. Also `if (completed) { try { await running; return; } … }`, with no check that `stepFinished` is true. Spec, "Deadline": "The deadline bounds each catch-up, from the start of its first round". "No fixed waits": "The deadline only bounds failure". Spec table: "Ogooreck passes the step as the function to run; catch-up is done when the wrapper returns."
Consequence: The spec and qa 52 leave these open, and the code decides them: (1) with `aroundStep`, a slow request or action is cancelled at the deadline and fails with the "still running" error, while the same step has no bound without `aroundStep`; (2) with both a wrapping and a plain catch-up, one step gets two full deadline budgets; (3) a wrapper that returns without calling `step` passes silently, so `ExpectNothingPublished` gives a false green and `ExpectResponse` reports a misleading message, and a wrapper that calls `step` twice runs the step twice. Searched spec.md "Deadline", "Recording and catch-up", the `aroundStep` row, and qa 52: none decides how the deadline applies to a wrapping catch-up, or what happens when the wrapper does not run the step exactly once.
Belongs to: spec
Resolution: fixed in spec r10 (qa 54): the coordinator settled it with the simplest consistent rule after Oskar asked for "just simples option"; open to his veto.

### Step-4. Criterion 11.1's action, as written, can't pass; the sample's test passes only because it adds an `Activity`

Quote: Spec/plan 11.1: "GIVEN `Action(ctx => { clock.Advance(TimeSpan.FromDays(1)); return Task.CompletedTask; })` as the When step … THEN it passes." Test: `.When(Action(ctx => { using var activity = AppApi.Traced(ctx.Traceparent); shop.Clock.Advance(TimeSpan.FromDays(1)); … }))`. progress.md: "The fake clock fires the expiry timer on the action's thread, which has no `Activity`, so without it `CartExpired` carries no trace id."
Consequence: The test checks 11.3's pattern (action starts an `Activity` parented on `ctx.Traceparent`), not 11.1. 11.1's literal code fails: `CartExpired` has no trace id, so the exact check sees 0 messages. The spec presents that form as a working example, and step 6 builds README snippets from the samples, so users copying it get a failing test with no hint why. The spec should either show the `Activity` wrapping in 11.1, or decide that Ogooreck runs actions under an `Activity` parented on the step's `traceparent` (the spec only says actions "receive it").
Belongs to: spec
Resolution: fixed in spec r10 (qa 54): Ogooreck runs actions and publish functions under an Activity parented on the step's traceparent.
