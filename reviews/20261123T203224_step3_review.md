### Step-1. 26.6 sets `pl-PL` on a thread that does not convert the attribute, so the invariant double format is not guarded

Quote: test `AttributeValues_AreStringsLikeJavaStringValueOf_UnderPlPlCulture` sets `CultureInfo.CurrentCulture = CultureInfo.GetCultureInfo("pl-PL")` on the test thread. The conversion runs in `InProcessTelemetry`'s `ActivityStopped = activity => spans.Add(SpanOf(activity))`, which calls `StringOf`, `IFormattable formattable => formattable.ToString(null, CultureInfo.InvariantCulture)`, on the thread that stops the request activity: the app's request thread inside `TestServer`. Spec "Telemetry": "integers and doubles formatted with the invariant culture (for example `1.5`)". Plan 26.6: "current culture `pl-PL` (set and restored in the test)". `InProcessTelemetryTests.InProcessSource_WritesValuesAsJavaStringValueOf_AndMarksTotalsAsCumulative` checks only `null`, an `int` and a list, with no bool, no double and no culture.
Consequence: `TestServer` does not keep the caller's `ExecutionContext` by default (`PreserveExecutionContext` is false, and the request is queued with `UnsafeQueueUserWorkItem`), so the culture, which flows as an `AsyncLocal`, does not reach the request thread. That thread runs under the process culture, which is `C.UTF-8` (invariant) on this machine and in CI. If `StringOf` formatted doubles with the current culture, `cart.total` would still be `1.5` and the test would still pass. Only the bool half (`True` against `true`) is guarded. A regression to culture-sensitive double formatting would ship unnoticed and would break users whose process culture is `pl-PL`.
Fix: stop an activity with `true` and `1.5` tags on the test thread while `pl-PL` is set (for example in `InProcessTelemetryTests`, or with a test `ActivitySource` inside an `Action` step as the 27.x tests do), and check `"true"` and `"1.5"`. Alternatively, set the culture inside the app for that request.
Belongs to: implementation
Resolution: implementation: fixed in the step 3 fix round, verified by ./build.sh test (single review round, per Oskar).

### Step-2. 28.5 does not exercise a missing baseline, and the cumulative "missing baseline counts as 0" path runs in no test

Quote: `MetricTests.ExpectMetric_CountsAMissingBaselineAsZero` checks `orders.placed`, a `Counter<int>`, which `InProcessTelemetry` records as a delta (`IsCumulative` false). `TestTelemetry.Increase` uses a baseline value only for cumulative series: `var before = series.LastOrDefault(each => each.BeforeBaseline).Measurement?.Value ?? 0;`. Spec "Telemetry": "Cumulative measurements: the latest value minus the series' baseline value. A series with no baseline value counts from 0, like Java's `before.getOrDefault(id, 0.0)`." Plan 28.5 test: "series tagged `cart.id` has no measurement before the When step; When records 1".
Consequence: delta sums never read a baseline value, so the test passes whatever a missing baseline does. The only cumulative series in the tests (`carts.open` in `ObservableMetricTests`) always has a value recorded at the baseline `Collect`. So the `?? 0` branch never runs. If it were changed to skip series with no baseline, or to treat them as unknown, no test would fail. Step 5's OTLP cumulative sums (29.2) depend on this rule.
Fix: add a cumulative series that first appears after the baseline, for example a `Gauge<T>` or an observable instrument tagged `cart.id = cartId` that only the When step records. Expect its increase to equal its value.
Belongs to: implementation
Resolution: implementation: fixed in the step 3 fix round, verified by ./build.sh test (single review round, per Oskar).

### Step-3. Cumulative series of different instruments with the same name and tags merge, so the increase depends on the order in which the listener reads instruments

Quote: `TestTelemetry`: `.GroupBy(each => SeriesOf(each.Measurement))` with `SeriesOf` = `SpanTree.Describe(measurement.Tags)`, then `series.Last().Measurement.Value - before`. `InProcessTelemetry` enables every instrument in the process (`InstrumentPublished = (instrument, listener) => listener.EnableMeasurementEvents(instrument, measurements)`), and the sample creates `carts.open` on a per-host meter (`IMeterFactory`). In `ObservableMetricTests`, `await using var spec = For<Program>();` is still alive while `other` runs, so both hosts' `carts.open {}` report into one series. Spec: "sums the increase since the baseline across series whose tags include `tags`". Progress: "28.4 runs in a serial collection on its own hosts".
Consequence: each `Collect` adds one value per live instrument. The series' "last" value then belongs to whichever instrument `RecordObservableInstruments` reads last, not to a sum across instruments. In 28.4's second half, the first host reports a constant 7 and the second host goes from 5 to 7. The test sees `found 2` only because the older host's instrument is read first. With the other order, or with any two live hosts whose instruments share a name (an assembly fixture plus a test's own specification), the increase comes out wrong, for example 0 instead of 2. A serial collection does not prevent this.
Fix, within the spec's `RecordedMeasurement` shape: in `InProcessTelemetry.Collect`, sum the observable values per instrument name and tags across instruments, and add one cumulative measurement per key. Alternatively, keep the instrument identity internally when grouping series. Add a test with two live hosts.
Belongs to: implementation
Resolution: implementation: fixed in the step 3 fix round, verified by ./build.sh test (single review round, per Oskar).

### Step-4. No test checks that disposing a specification disposes its telemetry source, or that each specification gets its own source

Quote: `ApiSpecification<TProgram>.Dispose()` calls `settings.Telemetry.DisposeAsync().AsTask().GetAwaiter().GetResult();` and `DisposeAsync()` calls `await settings.Telemetry.DisposeAsync();`. Plan extra: "inProcessSource_isNewForEachSpecification_andStopsRecordingOnDispose - covers two specifications each see only their own listener; after `Dispose()` the `ActivityListener` and `MeterListener` are disposed". Spec 5.1 and "Types": "Disposal stops the host, the telemetry source and the OTLP receiver." The implemented test creates two bare sources with `TelemetrySources.InProcess()`, calls `Attach` and `DisposeAsync` itself, and never creates a specification. `RecordingTelemetrySource.DisposeAsync` records nothing.
Consequence: removing both `settings.Telemetry.DisposeAsync()` calls, or sharing one default source across specifications, keeps every test green. Leaked listeners would keep sampling every `Activity` and recording every measurement in the test process for the rest of the run, which the spec's "Work added per operation" limits to "while a specification is alive".
Fix: let `RecordingTelemetrySource` count `DisposeAsync` calls, then dispose one specification with `Dispose()` and one with `DisposeAsync()` and check each source is disposed once. For "new for each specification", run a step on two `For<Program>()` specifications and check that a span stopped after the first one's disposal reaches only the second.
Belongs to: implementation
Resolution: implementation: fixed in the step 3 fix round, verified by ./build.sh test (single review round, per Oskar).
