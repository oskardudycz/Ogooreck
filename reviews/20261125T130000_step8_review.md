### Step-1. A variant of a variant starts a plug of the middle variant a second time

Quote: `if (!settings.IsPlugOfTheApp(owner)) starting.Add(start);` with `IsPlugOfTheApp(object owner) => app is not null && app.plugs.Contains(owner)`, and `if (parent is not null) await parent.EnsureStarted(step, ct);`. Plan: "their `Starting` runs once, through the parent". `PlugRegistration.Starting` doc: "Adds a function that runs once".
Consequence: `var first = app.With(s => s.Use(plug)); var second = first.With(s => s.Use(plug));` and one step on `second` runs the plug's `Starting` twice: once through `first`, once for `second`. Probe result: `Expected: 1, Actual: 2`. The shipped plugs survive it, because `KafkaConsumption.Start` starts only once, but a user's plug that opens a consumer in `Starting` gets two. Only plugs of the root count as "the app's", not plugs of the parents. `With_VariantOfAVariant_RunsOnTheSameApp` checks only the app instance.
Belongs to: implementation
Resolution: open

### Step-2. `WithNewApp` on a variant of a variant loses the middle variant's plugs

Quote: `foreach (var plug in root.plugs.Concat(app is null ? [] : plugs)) separate.Use(plug);`. Plan: "`WithNewApp(...)` build a specification with ... the root's and the variant's plugs, and the test setup copied".
Consequence: `app.With(s => s.Use(plug)).With(s => s).WithNewApp(s => s)` re-adds the root's plugs and the last variant's plugs, but not the plugs of the variant in between. That plug's recorders and catch-ups come along in the copied test setup, still bound to the shared app's `AppServices`, but its `Starting` never runs on the separate app. Probe result: `Expected: 1, Actual: 0`. If that plug is an option of an app plug (for example `Messaging.Kafka.CatchingUpWith(...)`), the root's plain plug replaces it, and the separate app runs without the option. Nothing fails. `WithNewApp_OfAVariant_KeepsTheVariantsTestSetup` covers one level only.
Belongs to: implementation
Resolution: open

### Step-3. The named forms ignore the recorder's role

Quote: `if (recorded is not null) return outcome.Recordings.FirstOrDefault(recording => ReferenceEquals(recording.Recorded, recorded)) ?? throw ...`. qa 98: "recorders have a role, as Java's two lists ... Oskar's rule from step 8 decided it: no case the API allows by mistake."
Consequence: `ExpectPublishedIn(Events.Marten.Appended, new OrderPlaced(cartId))` checks the Marten recorder of appended events as if it held published messages. It passes when the event was appended, and a failure lists the event under "Published by the When step". The probe printed exactly that for a recorder registered with `Appending(...)`. The same applies to `ExpectAppendedIn`, `PublishedIn`, `SentIn` and `AppendedIn` with a recorder of the other role. This is a case the API allows by mistake. The named lookup could filter by `wording.Role` as the unnamed one does, and fail with "registered with Appending(...), so check it with ExpectAppendedIn(...)".
Belongs to: implementation
Resolution: open

### Step-4. The "more than one recorder" failure names the wrong method outside `ExpectPublished`

Quote: `Name it with {wording.Check}In(...), for example {wording.Check}In(Messaging.Kafka.Published, ...).`
Consequence: the advice depends only on the role, not on the call that failed:
- `ExpectCausation(Published(...))` on the Kafka publish-only app says "Name it with ExpectPublishedIn(...)", which can't go inside `ExpectCausation`. The user needs `PublishedIn` or `SentIn`. Probe result: "ExpectCausation(...) found 2 recorders ... Name it with ExpectPublishedIn(...), for example ExpectPublishedIn(Messaging.Kafka.Published, ...)."
- `ExpectNothingPublished()` says to use `ExpectPublishedIn` instead of `ExpectNothingPublishedIn`.
- With two recorders of appended events, the example is `ExpectAppendedIn(Messaging.Kafka.Published, ...)`, a recorder of published messages.

Only the `ExpectPublished` text is tested, in `RecorderByRoleTests`.
Belongs to: implementation
Resolution: open

### Step-5. No test guards that the app keeps its telemetry after a variant is disposed

Quote: plan: "Disposing a variant disposes only its own telemetry"; tests `With_DisposingTheVariant_LeavesTheAppRunning` and `With_DisposedSynchronously_LeavesTheAppRunning` only compare `InstanceOf(app)`.
Consequence: a variant shares the app's `InProcessTelemetry`. If disposing a variant disposed that shared source, every `ExpectTrace` and `ExpectMetric` on the class fixture after the first variant's `await using` would fail, yet both disposal tests would still pass. A disposal test should run `ExpectTrace` on the app after the variant is gone.
Belongs to: implementation
Resolution: open

### Step-6. Sample tests that still start an app only for test setup, with no reason in progress.md

Quote: plan: "tests that built a specification only to change test setup use the shared app and `With(...)` ... per-cart and per-order scripting replaces app switches such as "without shipping"; tests whose app differs use `WithNewApp(...)` or keep their own explicit setup, each with its reason in progress.md." progress.md names no Marten change and no reason for these tests.
Consequence: each of these tests pays for an app start, and the Marten ones also create a schema:
- `Ogooreck.Sample.Wolverine.Tests/EventuallyTests.cs:34` uses `AppApi.WithDeadline(TimeSpan.FromSeconds(2))` only for a deadline. `api.With(s => s.Deadline(...))` gives the same app.
- `CatchUpTests.cs:71` does the same with `AppApi.WithDeadline(TwoSeconds)`. Here a heartbeat that never stops is a likely reason for an own app, but it isn't written down.
- `Ogooreck.Sample.Wolverine.Tests/CausationTests.cs:15` uses `AppApi.ShippingPlacedOrders()`. That is the "with shipping" app switch, which the step says per-cart scripting replaces.
- `ActionAndPublishTests.cs:22` uses `new AppApi()` for its own fake clock. That is a valid reason, because advancing a shared clock expires other tests' carts, but it isn't recorded.
- `Ogooreck.Sample.Marten.Tests/AppendedEventsTests.cs` has 7 tests with `MartenApi.WithCatchUp(database)`, each an identical own app with its own schema. They could share one app per class; only `WithoutCatchUp` and `WithStalledProjections` differ.
Belongs to: implementation
Resolution: open

### Step-7. Kafka group check describes each group with its own request, with no recorded reason

Quote: `var described = await Task.WhenAll(active.Select(group => admin.DescribeConsumerGroupsAsync([group], ...)));` replaced one `DescribeConsumerGroupsAsync(active, ...)`.
Consequence: every catch-up round and every first-step wait now sends one describe request per active group on the broker, instead of one. On the shared test broker, many groups are active at the same time, so the admin traffic per round grows with them. The step doesn't ask for this, and neither progress.md nor qa.md says why. If it fixes a failure seen with the batch call, that reason belongs in progress.md. Otherwise revert it.
Belongs to: implementation
Resolution: open
