# Review: spec r13

Reviewed: `spec.md` r13, `qa.md` up to 88. Earlier reviews: `20261123T164252_spec_r1_review.md`, `20261123T171500_spec_r2_review.md`, and the step reviews `20261123T174303_step1_review.md` to `20261123T211735_steps4-5_review.md`. Scope: the changes from r12 to r13 and what they affect.

## Q&A

Checked: the r12→r13 diff; spec r13 in full against qa answers 54–88, plus 15–17 and 50–53; the open notes in 58, 61, 63, 64, 66, 67, 73, 75, 76, 78 and 81–85, and whether later answers closed them; `Ogooreck.Sample.Kafka/Program.cs`, `Ogooreck.Sample.Kafka.Tests/{KafkaApi,TestAssembly}.cs`, `Ogooreck.Sample.Aspire.Api/Program.cs`, `Ogooreck.Sample.Marten.Tests/MartenApi.cs`, `Ogooreck.Sample.Wolverine.Tests/AppApi.cs`.

### Q&A-1. Answer 73's details are still open, but the spec states them as decisions, two of them as out of scope

Quote: qa 73: "**Open:** each of these is in spec r13 and plan r11 and waits for Oskar's yes or no." Answer 81 supersedes only items 6 and 8; answer 88 is a go-ahead for the review. The spec states items 1 (`Starting`, `AppServices`), 2 (`Services(...)` throws out of process, 36.4), 3 (one publish function, 36.3), 4 (resource-holding plugs belong to the caller), 5 (`messageType` matched on `FullName` then `Name`, JSON with web defaults), 7 (Out of Scope: "Recording Kafka's synchronous `Produce`"), 9 (Out of Scope: "Marten and Wolverine plugs for out-of-process apps"; "`RabbitMQPlug.Consuming` ... has no catch-up") and 10 ("All five packages get version 1.0.0 from the same `dotnet-1.0.0` tag") as firm. Item 9 also leaves qa 59's "I don't think that's entirely true that we can't override some stuff" open (`ASPNETCORE_HOSTINGSTARTUPASSEMBLIES`, not tested).
Consequence: the plan and implementation build on points Oskar never confirmed; a "no" on any means rework across the plug API, criteria 36 and the package layout.
Belongs to: qa
Resolution: accepted as written (Oskar: "pl", read as "ok", to all recommendations; qa 89)

### Q&A-2. The Kafka wait before the first step requires full assignment, which answer 83 rejected

Quote: spec: "Before the first step (`Starting`), it waits until every decorated consumer has all partitions of its topics assigned"; a few lines later: "after the decorated consumers have an assignment and no consumer group on the broker is rebalancing". qa 83: "the plug must wait for any assignment, then check."
Consequence: with a hidden consumer in the same group, the first rule times out "naming the consumer's topics", and the detection failure with its ways out (answer 86) never appears. The two sentences contradict each other.
Belongs to: spec
Resolution: fixed in r13: wait for any assignment and no rebalancing group

### Q&A-3. Several decorated consumers in one Kafka group or on one RabbitMQ queue were never spiked or decided, and the spec's own criteria create them

Quote: qa 80: "Not covered by the spikes: several consumers on one RabbitMQ queue; several decorated Kafka consumers in one group". Spec: "A test that needs other settings, such as a shorter deadline, uses another specification instance"; "Plugs are usually static fields shared by every specification of a test project"; criteria 39.5 and 40.6 use a second specification with a 2-second deadline.
Consequence: a second specification starts a second host whose `shipping` consumer joins the same group or queue under the same static plug. On Kafka neither consumer gets all partitions, so the wait never ends; on RabbitMQ the probe reaches only one consumer. The developer has to guess.
Belongs to: qa
Resolution: fixed in r13: one app per test project through an assembly fixture, or own group or queue names per app through test settings; documented, samples follow it

### Q&A-4. A missing registration fails with an app-side fix, and the Kafka plug fails apps that register no consumer

Quote: spec: "When nothing registers `TService`, the host fails to start, naming the type and saying that the app must register it" (37.2); "`KafkaPlug.Decorating<TKey, TValue>()` ... decorates the app's `IProducer<TKey, TValue>` and `IConsumer<TKey, TValue>` registrations". qa 87: "every way out is configured in the test project, never in the app." The Kafka and Aspire sample apps register only `IProducer<string, string>`.
Consequence: a producer-only app fails to start, and the failure tells the user to change the app, against answer 87. 39.1 doesn't say whether decorating the consumer is optional.
Belongs to: spec
Resolution: fixed in r13: the Kafka plug decorates the registrations that exist; the host fails only when neither exists

### Q&A-5. RabbitMQ `Ignoring` also removes the queue from catch-up, which no answer decided

Quote: spec: "`Ignoring(queues: string[])` leaves the named queues out of the check and out of catch-up"; Kafka: "leaves the named groups out of the check". qa 86 and 87 describe `Ignoring` as an override of the check only.
Consequence: in 40.7, ignoring `shipping` because of a foreign consumer also stops waiting for the app's own `shipping` consumer, so 40.2's "next step sees it shipped" breaks. Kafka and RabbitMQ behave differently with no answer behind it.
Belongs to: qa
Resolution: fixed in r13: RabbitMQ `Ignoring` skips the check only, as Kafka's

### Q&A-6. Answer 76's rule on clients the plug never saw is left out

Quote: qa 75: "A plug that never saw the app resolve its client (producer, consumer, connection) fails the first step and says why"; qa 76: "Decision: plugs fail loudly on setups they can't observe, never pass early". Answer 86 adds broker-side detection but doesn't withdraw the rule. The spec has no such failure; with zero resolved consumers the Kafka wait waits for nothing.
Consequence: a developer doesn't know whether a plug with no resolved client fails the first step (answer 76) or passes (the spec). Failing breaks producer-only apps; passing can end early.
Belongs to: qa
Resolution: fixed in qa 89: answer 76's rule is replaced by answer 86's precise check

### Q&A-7. The documentation and coverage gates now include the plug packages, which answer 55 didn't cover

Quote: spec Testing Decisions: "every public and protected member of the `Ogooreck` library and of the four plug packages"; "coverage of the `Ogooreck` library and of each plug package". qa 55: "100% line and branch coverage of the `Ogooreck` library", before the plug packages existed.
Consequence: 100% branch coverage of `Ogooreck.Kafka` and `Ogooreck.RabbitMQ` needs real-broker tests for every branch (`Management(...)`, `Assign()`, rebalancing, deadlines), a lot of plan work Oskar never decided.
Belongs to: qa
Resolution: accepted: the plug packages follow the same documentation and 100% coverage rule as core

### Q&A-8. The Node.js part of answer 57 is missing

Quote: qa 57: "and also be able to do it in Java and later Node.js in a moderatily similar way." The spec maps plugs only to Java.
Consequence: nobody checks the plug concepts (`IPlug`, `Decorate`, `CallRecorder`, `MessageReader`, plug options) against an Emmett shape, and the spec doesn't say whether Node.js is a follow-up.
Belongs to: spec
Resolution: fixed in r13: Node.js port listed as a later follow-up; plug concept names avoid .NET mechanisms

## Quality

Checked: spec r13 in full with focus on the diff hunks (plugging section, Hosts rule, criteria 36–41, configuration table, `PlugRegistration`, `Decorate`/`CallRecorder`, `MessageHeaders`/`MessageReader`, the four plugs, work added per operation, samples, documentation, mapping, testing decisions, out of scope); qa 52–88; the earlier reviews (no plug findings); `MartenApi.cs`, Wolverine `AppApi.cs`, `PublishedMessagesMiddleware.cs`, `PublishedMessagesTests.cs`, `KafkaApi.cs`, `KafkaBroker.cs`, `Ogooreck.Sample.Kafka/Program.cs`, core `StepCatchUp.cs` and `RecordingSource.cs`; RabbitMQ.Client 7.2.2 XML docs and assembly; Java `RabbitMQMessageBus.java`.

### Quality-1. How a test class overrides a shared plug is not defined, and the obvious reading records everything twice

Quote: "Every option (`Ignoring`, `CatchUp`) returns a new plug that shares the same `Published` recorder, so ... a test class overrides it in its own `Use(...)`"; "`Use(IPlug)` | Adds a plug ... Repeatable."; 39.8 "in that test class only"; "A test that needs other settings ... uses another specification instance."
Consequence: `Use` adds and never replaces. If `AppApi` uses `Messaging.Kafka` and a test class adds `Messaging.Kafka.Ignoring(...)`, two plugs decorate the producer and consumer, every produce is recorded twice into the shared recorder, two catch-ups run, and the original check still fails on `billing`. Options: a second `Use` of a plug from the same root replaces the first; the test class builds its own specification without `AppApi`'s `Use`; decorators deduplicate. 39.8 can't be written until this is settled.
Belongs to: qa
Resolution: fixed in r13: a plug made from another through an option replaces it in `Use(...)`

### Quality-2. Plug state shared by several specifications is undefined

Quote: "Plugs are usually static fields shared by every specification of a test project"; "`Use(plug)` calls `plug.Plug(registration)` at once."; "A member that is neither a decorated consumer nor the plug's own fails the step"; "`Starting(...)` functions run once".
Consequence: with `IClassFixture<AppApi>`, each test class has its own host, in parallel, all on the same static plug. Per plug: one host's catch-up waits on another host's consumers. Per host: every parallel host's `shipping` consumer is "not a decorated consumer" and the check fails. The same choice applies to the RabbitMQ consumer count and to `KafkaPlug.Consuming`'s consumer.
Belongs to: qa
Resolution: fixed in r13: same resolution as Q&A-3; plug state stays per plug

### Quality-3. The pre-step wait asks for full assignment, which answer 83 found must be "any assignment"

Quote: "it waits until every decorated consumer has all partitions of its topics assigned"; qa 83: "the plug must wait for any assignment, then check."
Consequence: the same as Q&A-2: a developer builds the wait the spike showed times out.
Belongs to: spec
Resolution: fixed in r13: same as Q&A-2

### Quality-4. Plugs can't see the deadline, but the Marten and Wolverine waits need it as a `TimeSpan`

Quote: Marten: "waits with `WaitForNonStaleProjectionDataAsync` through `AppServices`, bounded by the deadline"; Wolverine: "`TrackActivity().ExecuteAndWaitAsync(...)`"; `PlugRegistration` has no deadline member.
Consequence: both waits take a timeout; today `MartenApi` hard-codes 30 s and `AppApi` passes the deadline times 2. Options: expose the deadline on `PlugRegistration`, hard-code a timeout, or an infinite timeout raced against the token. With a hard-coded one, "fails after about 2 seconds" can become a tool timeout at another time with another message. The same applies to bounding `Starting`.
Belongs to: qa
Resolution: fixed in r13: `PlugRegistration.Deadline`

### Quality-5. An unknown `messageType` on any recorded message fails the expectation, even when the message isn't the When step's

Quote: "A message whose type header is missing or matches no type fails the expectation that reads it"; 38.3; "Messages from Given steps, from other tests on the same broker, and late arrivals don't count."
Consequence: core reads every item through `read` before it filters by trace id (`RecordingSource`), so a Given step's unlisted type, or another test's message seen by `KafkaPlug.Consuming`, fails a test whose own messages are fine; this breaks 16.1 and 18.4. Options: fail on any unknown item; fail only on items attributed to the When step (read the `traceparent` first); skip unknown items.
Belongs to: qa
Resolution: fixed in r13: `UnknownMessage`; fails only for the When step's messages

### Quality-6. `MessageReader`'s input shape in core is not defined

Quote: "`MessageReader` turns a broker message's headers and body into an `Observed`"; "`Recorded<KafkaMessage<TKey, TValue>>`"; "`Recorded<RabbitMQMessage>`".
Consequence: core references no broker client, so `MessageReader` needs its own input types, and the spec names none: header types (Kafka `byte[]`, RabbitMQ `object?` with strings as `byte[]`), text encoding, body as `string` or bytes, what "deserializes the body as JSON" means for a `TValue` the app serializes itself, and the shapes of `KafkaMessage<,>` and `RabbitMQMessage`. A user writing a plug for another tool can't tell what to pass.
Belongs to: qa
Resolution: fixed in r13: `MessageReader.Read(Func<string, string?> header, ReadOnlyMemory<byte> body)`, UTF-8 headers; other value types need a custom `Read`

### Quality-7. `CallRecorder` handles `Task` only, but RabbitMQ.Client 7's publish and ack methods return `ValueTask`

Quote: "For a method that returns a `Task`, it records when the task completes successfully"; "It records each `BasicPublishAsync` that succeeds"; "Each `BasicNack` or `BasicReject` with requeue ... counts as pending".
Consequence: `BasicPublishAsync`, `BasicAckAsync`, `BasicNackAsync` and `BasicRejectAsync` return `ValueTask` (the reviewer saw it in the 7.2.2 assembly references; a reflection check timed out). As written, `CallRecorder` would record at return, before the publish completes, and record failed publishes too; a `ValueTask` must not be awaited twice. Also unstated: whether the recorded `ReadOnlyMemory<byte>` body is copied.
Belongs to: qa
Resolution: fixed in r13: `CallRecorder` handles `Task`, `Task<T>`, `ValueTask`, `ValueTask<T>`; the RabbitMQ plug copies recorded bodies

### Quality-8. `Decorate` fails when the app registers nothing, but the Kafka plug always decorates both producer and consumer

Quote: 37.2; "decorates the app's `IProducer<TKey, TValue>` and `IConsumer<TKey, TValue>` registrations"; 39.1.
Consequence: a producer-only app (today's Kafka sample) or a consumer-only app fails to start. Options: decoration optional per type; both required; a non-throwing `Decorate` variant, which the spec doesn't give. The same applies to RabbitMQ.
Belongs to: qa
Resolution: fixed in r13: same as Q&A-4

### Quality-9. `CatchUp(...)` means "add" on the specification and "replace" on a plug

Quote: "`CatchUp(Func<CancellationToken, Task>)` | Adds a catch-up function ... Repeatable."; Kafka: "`CatchUp(Func<CancellationToken, Task>)` replaces the plug's catch-up and its check"; failure text "or .CatchUp(...) with your own wait."
Consequence: one name, two behaviors. A user who reads the failure and calls `spec.CatchUp(...)` adds a wait and keeps the failing check.
Belongs to: qa
Resolution: fixed in r13: the plug option is `CatchingUpWith(...)`

### Quality-10. The Wolverine plug's recording scope differs from today's middleware and is not defined

Quote: "`WolverinePlug` registers middleware that records each published envelope ... as the Wolverine sample does now (answer 52)".
Consequence: today's `PublishedMessagesMiddleware` is handler-chain middleware filtered to the sample's namespace, so it records only envelopes a local handler runs for. A generic plug can't hard-code a namespace. Options: all handled chains (includes Wolverine-internal messages, breaks exact checks); a type or namespace filter option; true publish-side recording.
Belongs to: qa
Resolution: fixed in r13: `MessageTypes(...)` option; plan part 7a spikes the recording hook first

### Quality-11. Sample tests lose the evidence they rely on when the setup classes keep only app settings and `Use(...)`

Quote: "Their setup classes ... keep only app settings, such as connection strings, and `Use(...)` calls"; "Ogooreck reads the channel; user code never does."
Consequence: the Wolverine tests assert on `AppApi.EveryPublishedMessage` (`PublishedMessagesTests.cs:31, 100, 116, 146`) to prove a Given step's or a late message was in fact published, so 16.1 and 16.4 don't pass vacuously; `KafkaBroker.EveryPublishedMessage` does the same. Options: drop the assertions (weakens 16.1 and 16.4); keep a side channel next to the plug; add a read API to the plugs.
Belongs to: qa
Resolution: fixed in r13: proof-of-publication checks stay as test code next to the setup class

### Quality-12. `RabbitMQPlug.Consuming` has no criterion, no sample, and an unspecified binding key

Quote: "`RabbitMQPlug.Consuming(Func<Task<ConnectionFactory>> connection, string[] exchanges)` ... binds its own exclusive queue to each exchange and records each message." Criterion 40 covers only `Decorating`.
Consequence: nothing proves it, and the binding key decides what it sees (`#` for topic, any for fanout, direct can't bind to everything, headers needs arguments). The plug option `CatchUp(...)` also has no criterion showing that it removes the check.
Belongs to: qa
Resolution: fixed in r13: `RabbitMQPlug.Consuming` dropped; out-of-process RabbitMQ is out of scope

### Quality-13. Criterion 36.2 has no concrete values and no observable result

Quote: 36.2 "THEN the specification behaves as if those calls had been made on it directly, and the services are registered in the test host only."
Consequence: "behaves as if" names no message, step or result, and "registered in the test host only" has no observable. A test that only checks the scenario passes would also pass if `Use` did nothing.
Belongs to: spec
Resolution: fixed in r13: 36.2 rewritten with concrete values

Approved: all recommendations, Oskar: "pl" (read as "ok").
