### Step-16. `CreatedId()` on a 201 without a usable `Location` fails with an `ArgumentOutOfRangeException` that names no step and says nothing about what was expected

Quote: TestStep.cs:169 `public string CreatedId() => FirstCreated().GetCreatedId();` and :172 `CreatedId<T>() => FirstCreated().GetCreatedId<T>();`. HttpResponseMessageExtensions.cs `GetCreatedId<T>` does `: throw new ArgumentOutOfRangeException(nameof(response.Headers.Location));`, and `TypeDescriptor...ConvertFromInvariantString` throws for an id that does not convert to `T`; `CreatedId` catches neither. spec.md:362: "Every failure Ogooreck throws is clear and precise about the issue (answer 48). It names what failed and where: the phase (Given step n or When), the step kind ... It also says what was expected and what was observed." spec.md:347: `CreatedId() ... // first 201's Location, via GetCreatedId`.
Consequence: if the first 201 has no `Location` header (common for a POST that returns only a body), or its last segment does not convert to `T` (for example `CreatedId<int>()` on a GUID id), the test fails with "Specified argument was out of the range of valid values. (Parameter 'Location')" or a bare converter error. The message does not say which step, which response or what the header held. Only the "no 201 at all" case (8.3) gets a location-aware message. No test covers either path.
Belongs to: implementation (spec.md:362 decides it; `CreatedId` can wrap the `GetCreatedId` failure with its step text, the response's request and the `Location` value it found)
Resolution: implementation: fixed in the final step 1 round. Per Oskar ("Could you focus and don't have dozens of round?"), it is verified by ./build.sh test, not re-reviewed.

### Standards-9. The new public `AssertionException` constructor's XML doc says it repeats the inner message, but it does not

Quote: Assertions/AssertionException.cs: `/// <summary>Creates a failure caused by another error, whose message the failure repeats.</summary> public AssertionException(string message, Exception innerException) : base(message, innerException) { }`. The constructor passes `message` through unchanged; only the caller repeats the inner message, for example ApiSpecification.cs:171 `"... The JSON parser reported: {exception.Message}"`. spec.md:363: "A wrapped error keeps the original as the inner exception and repeats its message in the outer one."
Consequence: `AssertionException` is public. A caller who trusts the doc writes `new AssertionException("Body check failed", inner)`, and the outer message does not contain the inner one, which breaks the spec.md:363 rule while the doc says it holds. Either the doc says what the constructor does, or the constructor builds the repeated message.
Belongs to: implementation
Resolution: implementation: fixed in the final step 1 round. Per Oskar ("Could you focus and don't have dozens of round?"), it is verified by ./build.sh test, not re-reviewed.
