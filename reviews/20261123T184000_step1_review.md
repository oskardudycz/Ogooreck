### Step-11. An Action step can't see the `Then` token, so cancelling doesn't stop it

Quote: TestStep.cs:34-40 `internal sealed class ActionStep(Func<StepContext, Task> run) ... Run(HttpClient client, StepContext context, CancellationToken ct) { await run(context); return null; }` (`ct` is ignored). spec.md Scenario flow: "Cancelling `ct` stops steps, catch-up and waiting, and `Then` ends with `OperationCanceledException`." spec.md Steps: "`Action(Func<StepContext, Task>)`". `StepContext` has `Traceparent`, `Responses` and `CreatedId`, but no token.
Consequence: an action step that waits (a delay, a fake clock, a poll) runs until it finishes, so a cancelled `Then` can hang for as long as the action takes. The spec's signatures give the action no way to see the token, and the only alternative, `WaitAsync(ct)`, leaves the work running in the background. Neither spec.md nor qa.md decides which to do (searched for "cancel", "Action" and "StepContext"). It is low risk in step 1, where `Action` is only used for 23.10, but it becomes real in step 3 (criteria group 11).
Belongs to: spec (Steps and the `StepContext` type, next to Scenario flow). Options: give actions the token, for example `StepContext.CancellationToken`, or state that cancellation does not reach a running action.
Resolution: fixed in spec r6: settled from the spec text "Cancelling `ct` stops steps"; `StepContext.CancellationToken` added (qa 49).

### Step-13. 35.2 is not built: the cancellation message does not name `Then` or the When request, and the most common path is not wrapped

Belongs to: implementation
Resolution: implementation: sent back to the step 1 implementer in round 4, with the error-message rule (qa 48): every failure message in step 1 must follow it.
