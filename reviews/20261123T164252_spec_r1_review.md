### Q&A-1. Span and in-process metric attribution is narrowed to the When step's trace, which Java and answer 22 don't do

Quote:
- Spec: "Ogooreck then counts as "caused by the When step" only the messages, spans and in-process measurements that carry the When step's trace id."
- Spec: "Spans belong to the When step by trace id."
- Spec: "In-process measurements carry `Activity.Current`'s trace id at recording time and count only if it is the When step's."
- Q&A 22: "In-process, measurements count only when made inside the test's traces."
- Q&A 7 picks trace context only for "which recorded messages belong to the When step".
- Java `When.then` collects one `traceIds` set from every Given and When step and filters spans with `traceIds.contains(span.getTraceId())`. `correlationMismatchOf` groups spans by trace because it expects more than one trace.

Consequence: No answer moves spans or metrics to When-only, and the When-only rule breaks the Java `ExpectCorrelatedTrace` causation rule in a common case. Say a When span carries a `messaging.message.causation_id` from a message a Given step sent. The handler span for that message sits in the Given trace, which is filtered out, so the check fails with "no span handled that message". A developer must either build When-only, and tests ported from Java or Emmett fail, or follow the Java reference and answer 22, and the build contradicts the spec and acceptance criteria 26.4 and 28.2.
Belongs to: qa
Resolution: fixed in r2: "in general when it's unclear then do similarily as java version" (answer 31). Spans and in-process metrics use all the test's trace ids; messages stay with the When step.

### Q&A-2. The non-generic `For(...)` entry point from answer 27 is gone, and no answer removed it

Quote:
- Q&A 27: "`For(Func<HttpClient>)` defaults to `ApiJsonSettings.Web`, telemetry off, and a 30-second deadline."
- Q&A 30 changes only the argument: "A base address ... This refines answer 18".
- Q&A 29: "`ApiSpecification.For<TProgram>()` returns the same type, for fixtures."
- Spec Types lists only the non-generic constructor that takes a configuration function and `ApiSpecification.For<TProgram>()`.
- Acceptance criteria 4.1 and 4.3: "GIVEN a non-generic `ApiSpecification` with `.Host(...)`".

Consequence: A developer must guess how an Aspire test creates its specification: a public parameterless constructor followed by fluent `.Host(...)`, a non-generic `For()` or `For(Func<Task<Uri>>)`, or only the subclass constructor. The fixture pattern from answer 29 has no documented entry point for out-of-process hosts.
Belongs to: spec
Resolution: fixed in r2: "Yes, fix as suggested" (answer 34). Non-generic `ApiSpecification.For(Func<Task<Uri>>)` added.

### Q&A-3. The source of the OTLP proto types is left open

Quote: Spec: "Core gains a dependency on `Google.Protobuf` and the OTLP proto message types (from an existing package if one provides them, otherwise compiled from the OpenTelemetry proto definitions at build time)." Q&A 19: "This adds an OpenTelemetry proto dependency." Q&A 26: "Core `Ogooreck`. Every user gets the protobuf dependency."
Consequence: The answers settle that the dependency exists and that it lives in core, but not which package or build step supplies the types. That either/or changes the package graph every user gets, and may add `Grpc.Tools` or a code-generation step to the build. The developer would pick one alone.
Belongs to: qa
Resolution: fixed in r2: "I wouldn't definitely be doing some custom build unless it's justified", then "Hand-decode the subset" (answer 32).

### Q&A-4. The documentation leaves out the guidance answers 22 and 23 asked for

Quote: Q&A 22: "The docs say to filter by a test-unique tag or run metric tests serially." Q&A 23: "It is never on by default, and the docs prefer a catch-up function." Consequence: The docs won't warn that out-of-process and observable metrics count other parallel tests, so users will write flaky `ExpectMetric` tests against Aspire. The migration guide presents `Eventually` as an equal replacement for `Until`, the opposite of answer 23.

### Quality-1. `Body(...)` must respect array order, but the comparer it is told to reuse ignores order

Quote: "`Body(object)` is a partial JSON match ... array order and length matter ... It uses `StructuralComparison`"; 23.3 "... `{"items":["a","b"]}` ... `Body(new { items = new[] { "b", "a" } })` ... THEN it fails, because array order matters."; Testing Decisions: "The existing `StructuralComparison` tests stay as they are."
Consequence: In `StructuralComparison`, `AssertEquivalent` compares nested collections without order. `CompareCollections` is ordered only for `IEnumerable<byte>`, and `AssertOrderedEquivalent` orders only the top-level list. If `Body` reuses it as written, 23.3 passes when it should fail. The developer has three options: change `StructuralComparison`, which changes business logic results (AC 33.1); add an ordered mode; or not use it for `Body`. The same question applies to nested collections in messages.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31). Ordered mode of `StructuralComparison` for `Body` and messages; business logic unchanged.

### Quality-2. `Observed`: the code shape and the text below it contradict each other on default parameters

Quote: "`public sealed record Observed(object Message, string? Traceparent, string? MessageId = null, ...)`" and "`Observed` carries no default parameters where F# would need named arguments. It is constructed positionally or through two constructors, with and without the ids."
Consequence: The developer must choose between optional parameters and a record with a 2-argument and a 5-argument constructor. The choice affects every `read` function and the F# sample.
Belongs to: spec
Resolution: fixed in r2: "Yes, fix as suggested" (answer 34).

### Quality-3. Configuration calls: no signature, and it is unclear whether a per-test call changes the shared fixture

Quote: "a constructor taking a configuration function, for subclasses"; "Each builder call replaces its default"; ACs 6.1, 13.2, 18.3, 22.3: "`.Deadline(TimeSpan.FromSeconds(2))`"; 2.3 "assembly fixture"; "`Host(Func<Task<Uri>> baseAddress)` ... (non-generic)" while "`ApiSpecification<TProgram>` derives from `ApiSpecification`".
Consequence: Four things are open:
- The configuration function's type.
- Whether calls change the instance or return a copy. Changing a shared fixture's deadline per test breaks parallel safety; a copy might start a second host.
- What the inherited `Host(Func<Task<Uri>>)` does on `ApiSpecification<TProgram>`.
- How a user gets a non-generic instance.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31). Configuration happens only before the first step; `Func` configure; host calls split by type.

### Quality-4. `Telemetry` names both a configuration method and a type, which breaks the subclass setup

Quote: "`Telemetry(ITelemetrySource)` | `Telemetry.Off`, ..."; "It can subclass `ApiSpecification<Program>`"; 6.2 "`.Telemetry(Telemetry.Off)`".
Consequence: Inside a subclass, `Telemetry` binds to the inherited method, so `Telemetry(Telemetry.Off)` fails with CS0119 (verified on .NET 10). There is a similar clash between the static `Published(...)`/`Appended(...)` factories and recorders named `AppApi.Published`/`AppApi.Appended`. Users would get compile errors in the recommended setup.
Belongs to: spec
Resolution: fixed in r2: "Yes, fix as suggested" (answer 34).

### Quality-5. `Scenario(...)` is listed as removed and as kept, with no meaning or acceptance criterion for the kept one

Quote: "`Scenario(...)`/`And(...)` continuations ... are removed."; "`Scenario(TestStep[] scenario, params TestStep[] more)`"; migration: "`Scenario(...)`/`And(...)` → Given steps and `StepContext`".
Consequence: The developer can't tell what the new `Scenario(...)` returns or whether it should exist. No acceptance criterion covers it.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31). `Scenario` is Java's step-joining helper.

### Quality-6. "New items" in a catch-up round counts every test's messages, so a shared recorder may never settle

Quote: "if any recorder received new items during the round, run another round; stop when a round adds none."; 2.3 "one host is started in total"; goal: "safely in parallel".
Consequence: With a shared host and in-app recorder, other tests' messages count as new items, so steps run extra rounds and can fail with "kept producing". The developer must decide between any items and only items with the step's trace id.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31). Any new item, like Java.

### Quality-7. The spec doesn't say whether `ExpectCausation` and `ExpectCorrelatedTrace` wait

Quote: "`ExpectTrace` ... waits until the tree matches"; "`ExpectCorrelatedTrace()` uses the Java version's rules"; "`ExpectCausation` ... fails if `read` returns no ids."
Consequence: Checking once can pass on an incomplete trace, or fail 27.4 before the handler spans finish. Waiting needs a completeness condition, which the spec doesn't define. `ExpectCausation` on a recorder without catch-up has the same gap.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31).

### Quality-8. Cumulative and observable metrics: no rule for a missing baseline or for when observable instruments are read

Quote: "Before the When step, Ogooreck records a baseline for metrics (per series)."; "latest value minus the baseline value per series"; 28.4 "... observable counter ... counts the increase across measurements matching the tags."; 29.2 tags with `cartId`.
Consequence: A series tagged with this test's `cartId` has no baseline point, so the developer must choose between counting a missing baseline as 0 and waiting for a second point. Observable counters report cumulative values only when `RecordObservableInstruments()` is called, and the spec doesn't say who calls it. Summing their values as deltas gives a wrong increase. 28.4 has no concrete values.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31). A missing baseline is 0; observable values are cumulative; `Collect`.

### Quality-9. The attribution acceptance criteria would pass without trace attribution

Quote: 16.1 (`ProductAdded` from a Given step, then `OrderPlaced`); 16.2 (two parallel tests, each with its own cart); 26.4 (a parallel span with the same name).
Consequence: 16.1 doesn't fix whether the recorder has catch-up, and subsequence matching passes anyway. In 16.2, each message has its own `cartId`, so both tests pass with no attribution. In 26.4, the matching span is present anyway. A broken trace-id filter would pass all three; only 16.4 and 28.2 would catch it.
Belongs to: spec
Resolution: fixed in r2: "Yes, fix as suggested" (answer 34).

### Quality-10. The source of the OTLP proto types is left open

Quote: "Core gains a dependency on `Google.Protobuf` and the OTLP proto message types (from an existing package if one provides them, otherwise compiled ... at build time)."
Consequence: The developer must choose between a third-party package and compiling the `.proto` files with `Grpc.Tools`/`protoc` and a pinned proto version. Every core user gets the dependency. This is the same as Q&A-3.
Belongs to: qa
Resolution: fixed in r2: same as Q&A-3 (answer 32).

### Quality-11. `Then` loses its cancellation token, and neither the spec nor the migration guide mentions it

Quote: "`.Then(params Expectation[])` returning `Task`".
Consequence: Today's sample tests call `.Then([CREATED, RESPONSE_LOCATION_HEADER()], ct)` with `Xunit.TestContext.Current.CancellationToken`. Without a token, migrated tests ignore framework cancellation for up to the 30-second deadline per wait.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31); the token overload is kept from the existing 0.x API.

### Quality-12. "The deadline" has no defined scope

Quote: "Expectations wait for their condition and fail at a deadline (30 seconds by default)."; "`Deadline(TimeSpan)` | Failure bound for catch-up and waiting expectations."
Consequence: The developer must choose between a deadline per catch-up and per expectation (a `Then` with three waiting expectations can take 90 s), one per `Then`, or one per test.
Belongs to: qa
Resolution: fixed in r2: "do similarily as java version" (answer 31). One deadline per catch-up and per waiting expectation.

### Quality-13. Decisions with no acceptance criterion

Quote: "`Json(JsonSerializerOptions)`"; "`Telemetry(ITelemetrySource)` ... or a custom source." with `ITelemetrySource { /* streams ... */ }`; "`Eventually` ... The other expectations then run once against that final attempt."; "`Satisfying(Func<HttpResponseMessage, Task>)`".
Consequence: The custom telemetry source is promised but `ITelemetrySource` has no members, so a developer must invent the interface. `Json(...)`, `Eventually`'s handling of the other expectations, and async `Satisfying` could be built wrong or left out, and no test would catch it.
Belongs to: spec
Resolution: fixed in r2: "Yes, fix as suggested" (answer 34).
