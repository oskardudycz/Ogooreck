### Step-1. The 29.4 test fails in the merged build: a previous test's late export lands after the baseline

Quote: `AspireApiTests.PlacingAnOrder_ExportsTheRequestDurationHistogramWithItsCount` failed with "When request POST /carts/4f51fd7b-.../orders: ExpectMetric(http.server.request.duration, {http.route=/carts/{id}/orders}, 1): expected an increase of 1 since the baseline, but found 2, which is more." The test runs on `AspireApi`, whose receiver is `OtlpReceiver.Start()` (no wait). Spec: "OTLP data arrives in periodic exports, so an increase from a Given step can arrive after the baseline. By default that is a documented limitation" (qa 37). Progress: "one test collection because the request duration histogram has no test-unique tag".
Consequence: `./build.sh test` is red. The collection already runs the Aspire tests one by one, so serial running is not the cause: the previous test's `POST /carts/{id}/orders` is exported after this test's baseline, and the cumulative series grows by 2. A test-unique tag is not available, because 29.4 fixes the filter to `{ ["http.route"] = "/carts/{id}/orders" }`, and adding one changes the criterion. An own host per test needs its own receiver too (the decoder drops resource attributes, so two apps on one receiver share series), and it costs an AppHost start. The fix within the spec: move the test to `WaitingAspireApiTests` (the `WaitForMetricsExport` receiver, same AppHost, same "Aspire apps" collection). Its baseline waits for exports that carry every earlier request, and the Given step uses another route (`/carts/{id}/products`). `PlaceOrder` works there, because the API skips Kafka when it has no connection string.
Belongs to: implementation
Resolution: implementation: fixed in the steps 4–5 fix round, verified by ./build.sh test.

### Step-3. WaitForMetricsExport waits for two exports; the spec and qa 37 say one

Quote: `OtlpReceiver.Collect`: `for (var export = 0; export < 2; export++)`. Spec "Telemetry": "`Collect` waits until the next metrics export arrives"; "Work added per operation": "With `WaitForMetricsExport`, each `Collect` waits for one metrics export (answer 37, opt-in)". qa 37: "its `Collect` waits for the next metrics export".
Consequence: the code follows a rule that the spec does not state. The reasoning in progress is right: the OpenTelemetry periodic reader collects, then sends, so the export in flight when `Collect` starts can have been collected before the Given step's increment. Only the export after it was collected after `Collect` started, so "the next export" does not make 29.5 hold. The cost is one more export interval per `Collect` (about 0.5 s in the sample), once at the baseline and on every `ExpectMetric` poll. Accept the code, and update spec "Telemetry" and "Work added per operation" and qa 37 to say "waits for the second metrics export to arrive after it starts, because the one in flight may predate the increment" (spec r12). The XML docs of `Collect` and `OtlpReceiverOptions.WaitForMetricsExport` already say this.
Belongs to: spec
Resolution: fixed in spec r12 (qa 56): the two-export wait is kept and the spec updated.

### Standards-2. A static OtlpReceiver on a fixture subclass dies with the first instance

Quote: spec 4.4: "`AspireApi : ApiSpecification` with a static `OtlpReceiver Otlp = OtlpReceiver.Start()` ... and `Telemetry(Otlp)` WHEN a test uses it as a fixture". Spec: "Disposal stops the host, the telemetry source and the OTLP receiver." `ApiSpecification.DisposeAsync` calls `settings.Telemetry.DisposeAsync()`, which stops the static receiver.
Consequence: the sample avoids it with `AssemblyFixture`, but a user who follows 4.4 with `IClassFixture<AspireApi>` in two test classes gets two instances over one static receiver. The first class's fixture disposal stops the receiver, and the second class's `ExpectTrace`/`ExpectMetric` fail at the deadline with no spans. The spec should either say the pattern needs one instance (an assembly or collection fixture), or say that a receiver passed in by the caller belongs to the caller.
Belongs to: spec
Resolution: fixed in spec r12 (qa 56) and code: a passed-in telemetry source belongs to the caller.
