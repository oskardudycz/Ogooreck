### Step-1. disposing_stopsTheHost passes even when the host is never stopped

Quote: StepTests.cs:229-245 `var spec = For<Program>(); HttpClient? kept = null; ... kept = client; ... spec.Dispose(); await Assert.ThrowsAnyAsync<ObjectDisposedException>(() => kept!.GetAsync(...))`. InProcessApiSpecification.cs:46-53 `host.Value.Client.Dispose(); factory?.Dispose(); defaultFactory.Dispose();`. Plan extra: "disposing_stopsTheHost - covers after `Dispose()`/`DisposeAsync()` a request through a client kept from the host fails". Spec: "Disposal stops the host".

The test can capture the factory through `Host(f => captured = f)`, or use a client the factory created, and show it fails after disposal.

### Step-3. The xUnit1051 suppression hides a usability cost of the spec's Then overloads

Quote: Ogooreck.Sample.Api.Tests.csproj:7 `<NoWarn>$(NoWarn);xUnit1051</NoWarn>`. Directory.Build.props `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`. Spec, Scenario flow: "`.Then(params Expectation[])` and `.Then(Expectation[] expectations, CancellationToken ct)`". progress.md: "Open question for Oskar: keep the suppression and document it, or change the signature."
Consequence: The code follows the spec's signatures, but because a `CancellationToken` overload exists, the xUnit v3 analyzer flags every `Then(...)` call without a token. Any xUnit v3 user project with warnings-as-errors fails to build on the README's own `Then(ExpectResponse(OK))` form unless it suppresses the rule too. The later xUnit sample projects (steps 2, 6 to 10) will each need the same line. The spec should decide whether to keep both overloads, and if so, the README should say how users handle xUnit1051.
Belongs to: spec (Scenario flow, the `Then` signatures; also Documentation)
Resolution: fixed in spec r4 / plan r3: "Pass the token in samples (Recommended)" (qa 43). Remove the suppression.

### Step-4. One shared HttpClient per specification is a decision the spec leaves open

Quote: InProcessApiSpecification.cs:37-43 `factory.CreateDefaultClient(new TraceparentHandler())`, created once inside `Lazy<StartedHost>`. Scenario.cs:44 `var (client, json) = host.Value;` hands that one client to every step of every test. Spec, Types: "The host (the factory, or the base address function and its client) starts on the first step and is reused for the specification's lifetime." For the in-process type, that line names only the factory; "its client" refers to the base-address case.
Consequence: A request step is "a plain function of `HttpClient`". A step that sets `client.DefaultRequestHeaders.Authorization`, or changes `Timeout` or `BaseAddress`, changes the client for every later step of every test on the same class fixture. Tests can run in parallel on one fixture (spec: "parallel tests on one shared host"), so this becomes a race. Neither spec nor plan decides whether the client is per specification, per scenario or per step, or whether steps may change it.
Belongs to: spec (Types, the host and client lifetime)
Resolution: fixed in spec r4 / plan r3: "Definitely we should be careful about performance, not recreating client host, unless it's needed. Check best practices and how Alba does it" (qa 44). Shared host and handler; a lightweight client per step (AC 23.13).

### Step-5. The in-process client no longer follows redirects, and the migration guide does not say so

### Step-7. Every response body is buffered, which the spec's list of added work does not include

Quote: TestStep.cs:21 `await response.Content.LoadIntoBufferAsync();` runs after every `Request` step. Spec, "Work added per operation" lists only catch-up, the `traceparent` header, telemetry, `Recorded<T>.Add` and `Collect`.
Consequence: For `GetAsync` and `PostAsJsonAsync` the content is already buffered, so this does nothing. Belongs to: spec (Work added per operation)
